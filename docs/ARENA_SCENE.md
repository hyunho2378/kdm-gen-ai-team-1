# ARENA_SCENE.md arena 1인칭 씬 설계

three.js 1인칭 승격의 씬 사양이다. DESIGN 9절의 레이어 목록과 1:1이다.
**수치는 구현에서 조정 가능하다.** 고정인 것은 규율(읽기 전용 경계, fx 계약, 폴백, 소유 색)이고 좌표와 시간은 튜닝값이다.

관련 문서: 입력 분리는 `ARENA_INPUT.md`, 판정 규칙은 `COMPONENTS.md`의 judge 항목, 색은 `DESIGN.md` 2절.
룰 심화(R 시리즈)의 사실 근거는 `FENCING_RULES.md`이고, 그 문서의 **채택 판정표가 본문보다 우선**한다.

---

## 0. 승격이 지키는 것

1. 게임 로직은 재활용한다. `machine.js`, `judge.js`, `opponents.js`는 **수정 금지**다.
2. 루프 주도권은 `loop.js`가 쥔다. react-three-fiber를 쓰지 않는다.
3. **렌더러는 게임 상태를 읽기만 한다.** 쓰기 0을 유지한다.
4. canvas 2D 렌더러를 삭제하지 않는다. 인터페이스 뒤의 폴백으로 남긴다.
5. 셀프테스트와 결정성 서명이 렌더 변경 뒤에도 그대로 나와야 한다.
   **D3에서 서명을 갱신했다.** AI 유파 다양화와 런지 추가는 의도적 게임플레이 변경이라 서명이 바뀌는 것이 정상이다.
   현재 기준: 셀프테스트 **8종**, 서명 **길이 244 / 해시 8c2f910 / 꼬리 `SCORE:6-2:53.633#6-2#ME`**
   (`judge.selftest.js`의 `BASELINE`이 원본이다).
   이전에는 앞 80자만 기록했는데 **그 구간은 D3 전후가 같았다.** 접두만 보는 가드는 회귀를 놓친다.

## 1. 렌더러가 읽는 게임 상태 (11개 확정)

이 표에 없는 필드에 렌더러가 접근하는 것을 금지한다.

| 필드 | 타입 | 의미 | 렌더 용도 |
|---|---|---|---|
| `d` | 0~100 | 간합 근접도. **클수록 가깝다** | 상대 빌보드 월드 z |
| `meLunge` | 0~1 | 내 런지 진행 | 검 그룹 자세 트윈 |
| `aiLunge` | 0~1 | 상대 런지 진행 | 빌보드 포즈, AI 검끝 |
| `meGuard` | bool | 가드 홀드 | 검 그룹 가드 자세 |
| `aiMode` | IDLE / TELEGRAPH / RECOVER | 상대 행동 단계 | 포즈 선택, 텔레그래프 강조 |
| `hitFlash` | 0~1 | 명중 섬광 감쇠 | 피격 포즈, 후처리 강도 |
| `hitOwner` | ME / AI / null | 마지막 명중 소유자 | 연출 방향 |
| `dilation` | 0~1 | 시간 팽창 강도 | AfterimagePass damp, 채도, 비네트 |
| `meLungeDeep` | bool | 이번 찌르기가 런지인가 | 더 깊은 뻗기 프리셋 선택(D3에서 추가) |
| `aiKind` | FEINT / REAL / null | 예고 종류 | **시각 스타일 전용(색감, 포즈 텍스처 선택). 타이밍 판정에 쓰는 것을 금지한다.** 타이밍은 `opponents.js`의 판정 영역이고 렌더러는 스타일만 건드린다 |
| `school` | 유파 객체 | 상대 유파 | **시각 스타일 전용. `aiKind`와 같은 등급이다(E4에서 추가).** `key` 하나만 읽어 표적 성향을 고른다(세이버 상단, 에페 몸통). 타이밍이나 판정 분기에 쓰는 것을 금지한다 |

`phase`는 렌더러가 읽지 않는다. HUD가 snapshot으로 따로 받는다.
`school`은 E4 전까지 이 표 밖이었다. **표를 늘릴 때는 D3(`meLungeDeep`)과 E4(`school`)처럼
문서를 먼저 고치고 개수를 갱신한다.** 표에 없는 필드를 조용히 읽는 것이 규율 위반이다.

## 2. fx 이벤트 계약

`engine.drainFx()`가 돌려주는 큐다. **2D와 three가 같은 계약을 받아야 폴백 전환에서 연출이 안 깨진다.**
스키마를 바꾸려면 두 렌더러를 함께 고친다.

### 스키마

| 필드 | 타입 | 설명 |
|---|---|---|
| `outcome` | `HIT` / `MISS` / `PARRY` / `RIPOSTE` | `judge.js`의 OUTCOME 상수 |
| `owner` | `ME` / `AI` | 그 결과의 주체 |

좌표는 담지 않는다. **명중 지점은 각 렌더러가 자기 검끝에서 스스로 구한다.**
2D는 화면 좌표, three는 검끝 월드 좌표를 카메라로 투영한다. 그래야 시점이 달라도 계약이 유지된다.

### 조합별 연출

| outcome | owner | 의미 | three 연출 |
|---|---|---|---|
| HIT | ME | 내 명중 | hitstop, 리본 흰 코어 고정, ShockWave, 색수차 스파이크, 셰이크 |
| HIT | AI | 피격(lose) | 위와 같되 Vignette 순간 강조, 셰이크 진폭 상향 |
| PARRY | ME | 가드 성공 | 금속 스파크, 짧은 셰이크, ShockWave 없음 |
| RIPOSTE | ME | 되찌르기 2점 | HIT/ME와 같은 시퀀스에 Bloom 순간 강조 |
| MISS | ME | 헛침 | **캔버스 연출 없음.** HUD의 JudgeText가 사유를 표시한다 |

`MISS`도 큐에 들어온다. 렌더러는 무시한다(현재 2D 동작과 동일).

## 3. 렌더러 인터페이스와 폴백

```
IRenderer:
  init(mount, tokens)
  resize(w, h)
  render(gameState, fx, dtRender)
  dispose()
  setPoses(images)
  setBackgroundImage(image)
  setSwordPose(pose)
```

### pose 객체 형태 (판별 유니온, 확정)

```js
// kind로 분기한다. 렌더러는 이 객체만 보고 입력 소스를 모른다.
{ kind: 'preset',     value: 'rest' | 'thrust' | 'guard' }
{ kind: 'quaternion', value: [x, y, z, w] }   // 캘리브레이션 보정이 이미 적용된 값
```

- `kind === 'preset'` → 렌더러가 5절 프리셋 좌표 사이를 `tokens.motion.thrust` 커브로 트윈한다.
- `kind === 'quaternion'` → 검 그룹 회전에 직결한다. 트윈하지 않는다(이미 30Hz 스트림이다).
- 형태를 여기 박아두는 이유는 C3 연결 때 어긋나지 않게 하기 위해서다. V4a에서 즉흥으로 정하지 마라.
- 값의 출처와 보정 지점은 `ARENA_INPUT.md` 3절을 따른다. 이 인터페이스는 소스를 모른다.

### 호출 위치 규율

`GameCanvas`가 루프 콜백에서 아래 순서를 지킨다. **이 순서를 렌더러 안으로 옮기지 않는다.**

```
render 콜백:
  1. loop.setTimeScale(engine.getTimeScale())   ← GameCanvas에 남긴다
  2. const fx = engine.drainFx()                ← 큐 소비도 GameCanvas가 한다
  3. renderer.render(engine.view, fx, realDtSec)
```

**`setTimeScale`은 로직 시계 제어라 렌더러 소관이 아니다.** 렌더러 안으로 딸려 들어가면
렌더가 로직 속도를 쥐게 되어 결정성 경계가 무너진다.
`drainFx`는 큐를 splice하는 소비 동작이라 상태 변경이다. 렌더러의 쓰기 0을 지키려면 호출자가 소비한다.

기존 `update(dt)` + `draw(view)` 2단은 `render()` 하나로 합친다.

### 폴백 3경로

| 경로 | 감지 | 동작 |
|---|---|---|
| WebGL 컨텍스트 생성 실패 | `init()`에서 예외 또는 컨텍스트 null | 즉시 `Canvas2dRenderer`로 생성 |
| 런타임 컨텍스트 손실 | canvas `webglcontextlost` | `dispose()` 후 2D로 교체, 경기 상태 유지 |
| 수동 강제 | URL `?renderer=2d`, dev 토글 | 처음부터 2D |

전환 시 StatusChip에 **"호환 렌더"**를 표시한다. 경기는 멈추지 않는다(PATTERNS 8절 우아한 저하).
`Canvas2dRenderer`는 기존 C1 3인칭 렌더러를 인터페이스에 맞춘 것이고 **동작은 변하지 않는다.**
`renderer/geometry.js`(검끝 좌표)는 로직이 참조하지 않으므로 `Canvas2dRenderer` 내부로 통째로 들어간다.

## 4. 카메라와 공간

- `PerspectiveCamera`, fov **70(수직)**, near 0.05, far 60. 눈높이 y 1.6m, 원점에서 -z를 본다. 미터 단위.
- **fov가 수직 기준이라 세로 프레이밍은 종횡비와 무관하다.** 가로는 넓을수록 여유가 생긴다.

### d → 상대 거리 매핑 (사양 정정)

**주의. 원 사양에는 "d 0 → 1.6m(초근접), d 100 → 6.0m(원거리)"로 적혀 있었으나 이는 `judge.js`와 반대다.**
`judge.js`는 d를 **근접도**로 정의한다("값이 클수록 가깝다"). `judge.js`는 수정 금지이므로 매핑을 뒤집는다.

```
dist(d) = 4.4 - (d / 100) * 3.1      // 미터
z_ai    = -dist(d)
```

상수는 **V4c에서 화면 점유율로 재조정했다.** 상대가 화면 높이에서 차지하는 비율은

```
점유율 = 1.9m / (2 x dist x tan35도) = 1.3568 / dist
```

이고, 유효 범위 d 35~55에서 40~55퍼센트를 차지해야 위협적으로 읽힌다.

| d | 거리 | 화면 높이 점유 | 비고 |
|---|---|---|---|
| 0 | 4.40m | 30.8% | 최원거리 |
| 35 | 3.32m | **40.9%** | 유효 범위 먼쪽 경계 |
| 45 | 3.01m | 45.2% | 경기 시작값 |
| 52 | 2.79m | 48.7% | 실측 대조 지점 |
| 55 | 2.70m | **50.3%** | 유효 범위 가까운쪽 경계 |
| 100 | 1.30m | 104% | 최근접 |

**실측 대조.** d 52에서 상대의 화면 세로 범위가 384~819px(1440x900)로 48.3퍼센트였다.
계산값 48.7퍼센트와 0.4퍼센트포인트 차이다(림 글로우 두께분).

근을 1.3보다 줄이면 d 100에서 상대가 얼굴을 뚫고 들어오고,
원을 4.4보다 키우면 먼쪽 경계가 40퍼센트 아래로 떨어진다. 그 사이가 이 두 상수의 여유다.

## 5. 내 검 (1인칭의 주인공)

### 구성

- 검 그룹(`Group`)에 검 모델을 담는다. **그룹 원점이 그립이고 칼끝은 원점에서 -z로 0.68m**다.
  프리셋 자세와 찌르기 트윈은 이 그룹이 쥔다. 모델이 바뀌어도 그룹 규약은 그대로다.
- 실물 모델은 **Antique Rapier Sword**(GabrielUCG, CC-BY-4.0) glTF다. 메시 6개에 머티리얼 1개를 공유한다.
  `Blade_low`만 머티리얼을 clone해 emissive를 `red.light`로 얹고 나머지는 원본 금속 텍스처 그대로 둔다.
  텍스처는 참조 공유라 clone에 추가 GPU 업로드가 없다.
- **칼끝 앵커**(`tipAnchor`)를 로드 시 1회 칼날의 자식으로 심는다. **이 지점이 내 리본의 소스다.**
  매 프레임 Box3를 다시 재지 않는다.
- 색은 전부 `tokens`에서 JS로 주입한다. 셰이더 유니폼에도 HEX를 적지 않는다.

### 모델 반입 규율

| 항목 | 규칙 | 이유 |
|---|---|---|
| 위치 | `arena/public/assets/sword/` | `scene.gltf`가 `.bin`과 텍스처를 **상대 경로 문자열**로 참조한다. `src/assets`에 두면 Vite가 .gltf만 해시 URL로 번들해 나머지가 404가 난다 |
| 정규화 | 바깥 컨테이너 그룹에만 회전과 스케일 | 내부 노드를 고치면 에셋 교체 때 전부 다시 해야 한다. Box3로 장축을 판별해 -z에 맞춘다 |
| 스케일 기준 | 칼끝이 그룹 원점에서 0.68m | 박스 검과 같은 값. 6절 궤적 좌표가 그대로 산다. 실측 스케일 0.758, 전장 0.79m |
| `frustumCulled` | 전 메시 false | 카메라 코앞의 1인칭 무기는 휘두를 때 바운딩 판정이 어긋나 순간적으로 사라진다 |
| 환경맵 | `scene.environment`(PMREM) 필수 | glTF의 metalness 높은 재질은 환경맵 없이 새까맣게 나온다(V4a에서 밟은 지뢰) |
| 로드 실패 | 박스 검 유지 + 콘솔 경고 | 검이 사라지는 상태를 만들지 않는다(PITFALLS 서드파티 원칙). 로드는 모듈 캐시로 1회뿐이다 |
| 텍스처 | 4096 → 1024 리사이즈, 파일명 유지 | 36.0MB → 3.8MB. 파일명을 유지해야 `scene.gltf` 수정이 필요 없다. PNG 유지(normal을 JPEG로 바꾸면 법선이 깨진다) |

### 마감 두 종과 득점 플레어 (D0 개정)

**상시 red emissive를 폐지했다.** 칼날에 레드를 늘 얹으면 레드가 배경색이 되어 득점 순간이 묻힌다.
DESIGN 2절 "검과 레드의 관계" 개정을 따른다.

| finish | 대상 | 처리 |
|---|---|---|
| `chrome` | 내 검 | baseColor 맵을 떼고 `steel.mid`로 덮어 청동 톤을 지운다. metalness 0.97, roughness 0.16. **노멀맵과 거칠기 맵은 유지**해 표면 디테일과 마모 변주가 산다 |
| `antique` | 상대 검(D2) | 원본 그대로. 역사 속 검객이라는 서사를 골동 재질이 진다 |

맵을 유지한 채로는 픽셀별 색을 못 바꾸므로, 색을 갈려면 baseColor 맵을 떼는 수밖에 없다.
둘 다 PMREM 환경맵이 서 있어야 발색한다.

**득점 플레어.** `fx`에 HIT 또는 RIPOSTE가 owner ME로 들어오면 `setFlare(1)`이 서고
`dtRender / 0.8`로 깎여 JUDGE 800ms 안에 죽는다.

```
emissive          = lerp(steel.mid, red.light, t)
emissiveIntensity = 0.06 + 1.8 * t^2
```

제곱이라 솟았다 빠르게 빠진다. 색까지 옮기므로 평시에 붉은 기가 남지 않는다.
피크에서는 블룸을 넘긴다. **이 순간은 넘기는 것이 맞다.** 레드는 사건의 색이다.

궤적 리본의 소유 색(내 `red.light`, 상대 `blue.light`)은 그대로다. 칼날이 크롬이어도 궤적은 색을 가진다.

### 자세 우선순위 (R1)

**thrust > guard(홀드 중) > 디폴트.** 이 순서를 두 곳이 똑같이 지킨다.
`GameCanvas`의 프리셋 결정부와 `ThreeRenderer.poseSword`다. 한쪽만 고치면 프리셋과 실제 자세가 어긋난다.

R1 전에는 가드를 먼저 봐서 찌르기 분기가 통째로 죽었다. 그래서 **가드를 문 채 되찌르면
찌르기 자세가 아예 안 나왔고** 리포스트가 화면에서 "찔렀다"로 안 읽혔다.
`judge.js`는 guard on/off를 순간 이벤트로 이미 옳게 처리하므로 **고칠 곳은 자세 채널뿐이다.**

가드 자세는 `guard_on ~ guard_off` 구간에만 선다. 홀드 진행도를 0~1로 두고 트윈한다.

| 방향 | 시간 | 근거 |
|---|---|---|
| 진입 | 55ms | 가드는 반응이다. 지연이 보이면 직접성이 무너진다(MOTION 1절) |
| 이탈 | 220ms | E1의 회복 값을 그대로 쓴다. 공격은 빠르고 회복은 느리다는 규칙이 검에도 같이 걸린다 |

찌르기 와인드업의 **출발은 지금 있는 자리**다. 가드 중이면 방어선에서 당겨지므로 되찌르기가
막기에서 이어져 보인다. 뻗기 구간은 와인드업에서 시작하므로 출발 자세와 무관하다.

**이 우선순위는 폰 쿼터니언(C3)에도 같이 걸린다.** 쿼터니언은 검 그룹의 회전만 덮어쓰고
그립 위치는 이 블렌드가 계속 쥐므로, 폰으로 찌를 때도 찌르기가 가드를 덮는 순서가 유지된다.

실측(60fps 환산): 가드 홀드 중 찌르기 칼끝이 가드 없이 찌를 때와 **차이 0.0000m**로 완전히 같다.
가드만일 때 대비 칼끝이 1.125m 이동한다. 진입 4프레임(67ms), 이탈 14프레임(233ms)으로
프레임 양자화 오차 안에서 설계값과 일치한다. 블렌드 전 구간에서 6절 안전 부등식은
최대 |ndcY| 0.823 / |ndcX| 0.700으로 한계 0.92 아래다.

### 자세 소스 두 갈래

- **키보드 모드**: 위 프리셋 사이를 `tokens.motion.thrust` 커브로 트윈한다. 이번 승격 범위는 여기까지다.
- **컨트롤러 모드(C3)**: 캘리브레이션 오프셋을 적용한 쿼터니언을 검 그룹 회전에 직결한다.
  이번에는 **입력 슬롯만 인터페이스로 파둔다**(`setSwordPose({ kind: 'quaternion', value: q })`).
  실제 연결은 C3에서 한다. 3절의 판별 유니온 형태를 따른다.

### 찌르기 연출

그립이 z -0.55 → -1.5까지 thrust 커브로 뻗었다 복귀한다.
복귀는 뻗을 때보다 느리게 둔다(비대칭이 찌르기의 인상을 만든다).

## 6. 1인칭 궤적 가시성 증명

**승인 조건 항목이다.** 좌표를 화면에 투영해 실제로 보이는 영역을 계산했다.

투영식(카메라 로컬, z는 앞쪽이 음수):

```
ndcY = (y / |z|) / tan(fov/2)
ndcX = (x / |z|) / (tan(fov/2) * aspect)
화면X% = (ndcX + 1) / 2,   화면Y% = (1 - ndcY) / 2
```

fov 70 → `tan(35°) = 0.7002`. 프러스텀 안이려면 `|ndc| <= 1`, 안전 영역은 `|ndc| <= 0.92`로 둔다.

### 자세별 화면 위치 (16:10 기준)

| 자세 | ndcX | ndcY | 화면 X% | 화면 Y% | 판정 |
|---|---|---|---|---|---|
| 휴식 그립 | 0.454 | -0.779 | 72.7 | 88.9 | 안전 |
| 휴식 검끝 | 0.357 | -0.299 | 67.9 | 65.0 | 안전 |
| 와인드업 그립 | 0.584 | -0.906 | 79.2 | 95.3 | 안전(가장 빡빡) |
| 와인드업 검끝 | 0.489 | -0.511 | 74.4 | 75.6 | 안전 |
| 찌르기 그립 | 0.083 | -0.152 | 54.2 | 57.6 | 안전 |
| 찌르기 검끝 | 0.009 | 0.037 | 50.5 | 48.2 | 안전 |
| 가드 그립 | 0.428 | -0.286 | 71.4 | 64.3 | 안전 |
| 가드 검끝 | 0.159 | 0.540 | 57.9 | 23.0 | 안전 |

**모든 자세가 프러스텀 안이고, 시야각 밖으로 나가는 구간이 없다.**

### 궤적이 지나는 화면 영역

| 동작 | 경로 | 가로 스윕 | 세로 스윕 | 대각 |
|---|---|---|---|---|
| **찌르기 호** | 와인드업 검끝(74.4, 75.6) → 찌르기 검끝(50.5, 48.2) | 24.0% | 27.4% | **36.4%** |
| **가드 전환 호** | 휴식 검끝(67.9, 65.0) → 가드 검끝(57.9, 23.0) | 9.9% | 41.9% | **43.1%** |
| **페인트 대응 호** | 가드 검끝(57.9, 23.0) → 휴식 검끝(67.9, 65.0) | 9.9% | 41.9% | **43.1%** |

- **찌르기**는 화면 우하단 사분면(74%, 76%)에서 출발해 정중앙(51%, 48%)을 관통한다. 대각 36%를 가로지르는 스트리크다.
- **가드 전환**은 중앙 하단(68%, 65%)에서 상단(58%, 23%)까지 세로로 42%를 훑는다. 화면 세로의 5분의 2다.
- **페인트 대응**은 가드 호의 역경로다. 진입과 이탈이 같은 경로라 공간적 일관성(MOTION 9절)을 지킨다.

세 동작 모두 **화면 중앙부를 지나므로 리본이 시선 안에서 그려진다.** 1인칭 승격의 심미 이득이 성립한다.

### 종횡비별 여유

세로는 fov가 수직이라 종횡비와 무관하다. 가로만 검사한다.

| 종횡비 | 최대 \|ndcX\| | 판정 |
|---|---|---|
| 4:3 (1024×768) | 0.700 | OK |
| 16:10 (1440×900) | 0.584 | OK |
| 21:9 | 0.400 | OK |

가장 빡빡한 4:3에서도 0.700으로 여유가 있다. arena는 1024 미만을 차단하므로 이 범위면 충분하다.

### 자세 조정 규칙

수치를 바꿀 때 아래 두 부등식을 깨지 마라.

```
|y| <= 0.7002 * |z| * 0.92     (세로 안전)
|x| <= 0.7002 * aspect * |z| * 0.92   (가로 안전, aspect 최소 1.333 기준)
```

와인드업 그립이 ndcY -0.906으로 가장 빡빡하다. 그립을 더 내리려면 z도 함께 키워야 한다.

## 7. AI 상대 (빌보드)

- 정면 펜싱 선수 스틸 5포즈: 대기, 전진, 텔레그래프, 런지, 피격.
  **생성형 이미지 도착 전에는 코드로 임시 실루엣 텍스처를 만든다**(캔버스에 그려 `CanvasTexture`).
- 오프스크린 캔버스 **512 x 1024, 생성 1회 후 재사용**. 평면 2장이 같은 텍스처를 공유해 총 5장이다.
  텍셀은 정사각이다(512px가 0.95m, 1024px가 1.9m로 둘 다 539px/m).
  **정규 좌표는 비등방이다.** x의 0.1은 51px, y의 0.1은 102px이라 원형 머리는 x 반지름이 y의 두 배여야 한다.
- 재질은 `MeshBasicMaterial`. 실루엣이라 조명 계산이 필요 없고 값이 텍스처 그대로 나와 블룸 예측이 쉬워진다.
- 평면 2장을 겹쳐 크로스페이드로 포즈를 전환한다. 항상 카메라를 향한다(billboard).
  **공격은 빠르고 회복은 느리다(E1).** 텔레그래프와 런지와 피격으로 들어갈 때 55ms, 돌아올 때 220ms다.
  같은 값으로 두면 찌르기가 미끄러지듯 나가 순간성이 죽는다.
  3D 검의 손 추종도 같은 값을 쓴다. 몸이 빠르게 뻗으면 검도 같은 프레임에 나가야
  "검만 따로 논다"가 아니라 "몸으로 찌른다"가 된다.
  `renderOrder`는 빌보드 1, 리본 2다. 궤적이 상대 위로 지나간다.
- 월드 z는 4절의 `dist(d)`. 원근 스케일은 카메라가 알아서 처리한다.
- **앵커는 발바닥 기준이다.** 발을 텍스처 맨 아래에 두면 발 스트로크와 림과 글로우가 경계 밖으로
  나가 바닥에서 잘린 그루터기로 보인다(D1 실측). 발 중심을 v 0.952로 들이고
  머리 꼭대기 v 0.021과 발바닥 v 0.969 사이가 정확히 1.9m가 되게 평면 크기를 역산한다
  (`PLANE_H = 1.9 / (0.969 - 0.021) = 2.004m`). 그래야 4절 화면 점유율이 그대로 산다.
- **접지 그림자 블롭 1장.** 발밑에 눕는 방사 그라디언트 타원(`bg.deep`, 반투명, `depthWrite` false).
  빌보드 그룹의 자식으로 넣으면 카메라를 따라 일어서므로 씬에 직접 붙이고 z만 따라간다. 드로우콜 +1.
- **포즈 간 실루엣 차이가 커야 한다(E1).** 차이가 작으면 전환이 아예 안 읽혀 몸이 굳은 것처럼 보인다.
  런지는 대기 대비 머리가 텍스처 높이로 0.205(약 0.41m) 떨어지고 발 간격이 0.49에서 0.844로 벌어진다.
  앞무릎은 깊게 접히고 뒷다리는 펴진다.
- **텔레그래프 포즈는 어깨 들림이 실루엣만으로 구분되게 한다.** 색이 아니라 형태로 읽혀야 한다
  (DESIGN 13절 색 단독 구분 금지).

### 풋워크 (E4)

거리 축(z) 말고는 아무것도 안 움직이면 상대가 "서 있는 그림"으로 읽힌다. 포즈를 아무리 과장해도(E1)
포즈와 포즈 사이가 완전 정지라 살아 있지 않다. 그래서 그룹 변형을 얹는다. **텍스처 5장은 그대로다.**

| 성분 | 값 | 근거 |
|---|---|---|
| 좌우 잔발 | `position.x`, 진폭 0.045m | 실루엣 폭 1.002m의 4.5퍼센트. 프레임당 최대 **1.02mm**로 리본 순간이동 가드(350mm)의 **1/344**이라 궤적을 건드리지 않는다 |
| 호흡 | 세로 압축 0.6퍼센트 | 머리 11mm 상하 |
| 큰 숙임 변주 | 세로 압축 5.5퍼센트, 0.85초, 간격 3.4~6.8초 | 미세 잔떨림만 있으면 "떨고 있는 그림"이다. 이따금 크게 숙였다 일어나야 선수가 된다. 실측 평균 간격 5.04초, 숙임 중인 시간 16.9퍼센트 |
| 전진 / 런지 숙임 | 세로 압축 3.5 / 5.0퍼센트 | 무게중심 하강. 런지는 `aiLunge` 진행도에 비례한다 |

**노이즈는 시간의 함수여야 한다.** 매 프레임 난수를 더하면 그것은 떨림이지 발놀림이 아니다.
주기가 서로 나누어떨어지지 않는 사인 셋(0.83 / 1.61 / 2.87 rad/s)을 겹쳐 반복이 안 읽히게 한다.

**세로는 위치가 아니라 압축이다.** 그룹을 아래로 내리면 발이 바닥면 밑으로 들어가 잘린다.
지오메트리가 발바닥을 y 0에 맞춰 놓았고 바닥이 불투명이라 깊이가 발을 먹는다.
D1에서 고친 "잘린 그루터기"가 그대로 재발한다. 실제 펜서도 무게중심을 낮출 때 발은 지면에 붙어 있다.

**압축은 그룹이 아니라 빌보드 평면 2장에만 건다.** 그룹에 걸면 손에 붙은 3D 검까지 비균등 스케일을 받아
칼이 눌리고, 부모 비균등 스케일과 자식 회전이 겹쳐 전단까지 생긴다. 손 앵커와 겨냥점은 압축 비율만큼
y를 곱해 몸을 따라 내려온다. 그래야 검이 몸에서 떠 있지 않다. 접지 그림자는 x를 따라간다.

**예고 진입 순간 시간 자체를 세운다.** 공격 예고가 잔움직임에 묻히면 페인트 판독 게임이 죽는다.
**정지 자체가 "온다"는 신호다.** 값을 0으로 되돌리지 않고 그 자리에서 얼리므로 진입에 팝이 없고
(실측 0.0000mm) 재개도 얼었던 위상에서 이어진다(실측 0.16mm).
실측: 예고 15프레임 동안 변위 폭 **0.0000mm**.

화면 점유율은 압축을 먹어도 d 45에서 42.4~44.9퍼센트로 4절 요구(40~55)를 벗어나지 않는다.

### 표적 다양화 (E4)

상대가 늘 같은 곳을 노리면 공격이 한 장면으로 굳는다. **공격마다 표적을 다시 뽑는다.**
예고에 들어가는 순간 한 번 정하고, 예고 자세가 이미 그쪽을 겨누므로 어디로 오는지가 형태로 미리 읽힌다.
3D 검 겨냥이 그 방향으로 돌고 파란 리본이 그 궤적을 그린다.

| 표적 | 겨냥 보정 (dx, dy) |
|---|---|
| 머리 | (-0.10, +0.42) |
| 몸통 | (0, 0) |
| 옆구리 | (+0.26, -0.30) |

유파 성향은 가중 주머니 하나로 낸다. 실측 300회에서 세이버 머리 150 / 몸통 81 / 옆구리 69,
에페 몸통 150 / 옆구리 81 / 머리 69다. **시각 전용이다.** `judge.js`는 부위를 보지 않는다.

### 상대 검 (D2)

빌보드에 **3D 골동 레이피어**를 붙인다. 같은 로더에 `finish: 'antique'`만 넘긴다.
검 손 앵커(`hand`)를 빌보드 로컬에 두고 포즈마다 위치와 겨냥 방향을 바꾼다.
손 위치는 텍스처 좌표에서 그대로 나온다.

```
x = (u - 0.5) x PLANE_W      y = PLANE_H x (SOLE_V - v)
```

**겨냥을 카메라 정면으로 두면 검이 극단적으로 단축돼 점으로 보인다(실측).**
대기와 예고는 비스듬히 세워 화면을 가로지르게 하고, 런지만 카메라 쪽 성분을 키운다.

antique 마감은 baseColor와 노멀맵을 그대로 두되 `metalness 0.90 / roughness 0.30`으로 올린다.
원본 값 그대로는 블랙 무대에서 빛을 못 받아 검이 통째로 사라진다. 반사가 걸려야 청동 결이 보인다.

**AI 리본 소스는 이 검의 `tipAnchor`다.** 가상 오프셋 포인트는 검 로드 실패 시의 폴백으로만 남는다.

### 순간이동 가드 (리본 공통)

검끝이 한 프레임에 `max(0.35m, 12 m/s x dt)`보다 멀리 뛰면 이력을 버리고 그 자리에서 새로 시작한다.
포즈가 바뀌며 겨냥이 크게 돌 때 두 점이 벌어져 **화면을 가로지르는 거대한 띠**가 그려지는 것을 실측했다.
고정 거리로 두면 안 된다. 프레임이 길어지는 저성능 환경에서 정상적인 큰 걸음까지 잘려 리본이 통째로 사라진다.

### 블랙 배경 위에서 실루엣이 읽히는 법

**D2 개정. 흰 펜싱 유니폼 전제로 몸체를 밝게 채운다.** 블랙 무대 위 흰 선수가 우리 무채색 규칙과 정합이다.
밝은 몸체는 그 자체로 실루엣이 되므로 바깥 림에 기대지 않고, 대신 부위마다 어두운 테두리를 둘러
겹친 팔다리가 서로 갈린다(2패스. 굵게 어둡게 한 번, 그 위에 유니폼 톤으로 한 번).
마스크는 어두운 메시에 밝은 테두리, 장갑과 신발도 어둡게 얹어 선수로 읽히게 한다.
검은 텍스처에 그리지 않는다. 3D 검이 손 앵커에 따로 붙는다.

**유니폼 밝기 상한.** 순백은 선형 1.0이라 문턱을 넘어 상대 전체가 번진다.
steel.mid를 bg.deep으로 0.30만큼 눌러 sRGB 약 0.60에 앉힌다. 실측 167/255(선형 **0.386**)로 문턱 아래다.
배경 0.04 대비 15:1이라 블랙 무대에서는 이것이 흰색으로 읽힌다.
팀 이미지 제작 사양은 `OPPONENT_IMAGE_SPEC.md`를 따른다.

(폐기된 이전 규율) 어두운 채움 + 밝은 림. 어두운 실루엣을 그냥 올리면 배경과 붙어 사라진다.
머리:몸 비례 1:6.5, 투구에 턱 보호대와 비브를 붙여야 민머리가 아니라 펜싱 마스크로 읽힌다.

**림 밝기는 Bloom threshold 아래로 묶는다. 블룸은 궤적의 전유물이다.**
여기서 한 번 틀렸다. 알파 합성은 sRGB가 아니라 **선형 버퍼**에서 일어나므로 흰 림의
합성 결과 선형 휘도가 곧 알파다. 알파 0.52는 선형 0.58이라 threshold 0.42를 넘었고
실측에서 다리 구간이 192/255(선형 0.527)로 나와 상대 전체가 번지고 있었다.

| 항목 | 값 | 실측 |
|---|---|---|
| 림 알파 | 0.26 | 글로우 0.10과 합쳐 선형 0.334 |
| 화면 실측 | 159/255 | **선형 0.347 < 0.42.** 블룸 미적용 |
| 배경 대비 | sRGB 0.61 대 0.04 | 약 15:1 |

밝기를 낮춘 대신 림 두께를 키운다(반지름 3 → 5). 두께는 휘도를 올리지 않는다.
투구 하이라이트도 어두운 몸체 위에 얹히므로 알파가 거의 그대로 선형 휘도다. 0.30으로 묶는다.

### AI 검끝과 FEINT / REAL 구분

빌보드 앞쪽 오프셋 포인트를 포즈별로 애니메이션한다. 런지 시 카메라를 향해 뻗는다.
이 포인트가 AI 리본의 소스다. **샘플링은 `aiMode`가 IDLE이 아니거나 `aiLunge`가 살아 있는 구간에만 한다.**
대기 중에 계속 먹이면 움직이지 않는 검끝에 파란 얼룩이 상주한다. 끊겼다 이어질 때는 리본을 비운다.
그러지 않으면 옛 점과 새 점이 화면을 가로지르는 직선으로 이어진다.

`aiKind`는 **시각 스타일 전용**이고 타이밍 판정에 쓰지 않는다. 구분은 두 겹이다.

| 구분 | 1차(형태) | 2차(색조) |
|---|---|---|
| REAL 예고 | 검끝이 어깨 위로 크게 올라간다(로컬 y 1.76). 파란 리본이 큰 호를 그린다 | 림을 red.light 쪽으로 0.35 섞는다 |
| FEINT 예고 | 검끝이 가드 근처에서 짧고 낮게 튄다(로컬 y 1.26) | 중립 steel |

텔레그래프 텍스처는 한 장을 공유한다. 형태 구분은 **3D 검끝 궤적**이 지고 색조는 보조다.
색 단독 구분이 아니므로 DESIGN 13절을 지킨다.

### 피격 틴트

`hitFlash`와 `hitOwner`만 읽는다. **`judge.js`의 owner는 득점자다.** 따라서 `hitOwner === ME`가
"상대가 맞았다"이고, 이때 상대 빌보드가 붉어진다. 반대로 읽으면 내가 맞을 때 상대가 붉어진다.

| 연출 | 조건 | 지속 |
|---|---|---|
| red.light 틴트 | `(hitFlash - 0.808) / 0.192` | **120ms**(hitFlash 감쇠 1.6/s 기준) |
| 피격 포즈 | `hitFlash > 0 && hitOwner === ME` | **633ms**(JUDGE 800ms 안) |

실측: 엔진 단독 구동에서 세 번 모두 `owner: ME`, 틴트 133ms(스텝 경계 포함), 피격 포즈 633ms.

## 10. 포스트프로세싱 파이프라인

`postprocessing`(Zlib). 합성 순서는 아래를 지킨다.

```
RenderPass
  → EffectPass(TextureEffect)   잔상. 직전 합성 결과를 damp만큼 덮는다
  → SavePass                    이번 결과를 다음 프레임용으로 저장
  → EffectPass(                 EffectPass 자동 병합으로 패스 수를 줄인다
       BloomEffect,                 궤적 발광
       ChromaticAberration,         평시 0
       VignetteEffect,              평시 약하게
       HueSaturationEffect          평시 0
     )
  → ShockWaveEffect             명중 시 트리거
```

**`postprocessing`에는 AfterimagePass가 없다(v6.39 전수 확인).**
three의 `examples/jsm`에 있는 것은 다른 EffectComposer의 Pass라 이 컴포저에 꽂히지 않는다.
그래서 같은 식을 이 라이브러리의 기본기로 세운다. `SavePass`가 직전 합성 결과를 들고 있고
`TextureEffect`가 그것을 NORMAL 블렌드로 덮는다. opacity가 damp이므로

```
out = current x (1 - damp) + prev x damp
```

로 AfterimagePass와 같은 식이 된다. `SavePass`는 블룸 앞에 두어 잔상이 블룸을 되먹이지 않게 한다.

### 잔상 damp

| 상태 | damp | 근거 |
|---|---|---|
| 평시 | **0.70** | 60fps에서 n프레임 뒤 잔량은 damp^n이다. 한 호흡(0.3초 = 18프레임) 안에 1/255 아래로 내려가려면 damp < 0.735여야 한다. 0.70은 18프레임 뒤 0.0016(0.4/255)이고 10퍼센트까지 108ms를 남긴다 |
| 시간 팽창 | 0.92 | 설계값 유지(V4e) |

**0.82는 폐기한다.** 0.47초를 끌어 과했다(실사용 피드백). 프레임 수 계산은 블렌드 식에서 나온 정확값이다.

**`ShockWave`는 render 루프에 `delta`를 반드시 전달한다.** 누락이 흔한 버그다(조사 19절).

### EffectPass 병합이 안 되는 조합 (D5 실측)

10절 초안은 Bloom과 ChromaticAberration과 ShockWave를 **한 EffectPass에 묶는** 것이었다. 안 된다.

```
Effects that transform UVs are incompatible with convolution effects (ShockWaveEffect)
```

Bloom은 컨볼루션이고 ShockWave와 ChromaticAberration은 UV를 옮긴다. 병합은 이 라이브러리의 요령이지만
이 조합에서는 성립하지 않는다. **합성 순서는 그대로 두고 패스만 셋으로 가른다**
(`EffectPass(bloom)` → `EffectPass(chromatic)` → `EffectPass(shock)`).
풀스크린 패스가 둘 늘어 드로우콜이 41 → 43이 됐다.

이 예외가 던져졌을 때 **폴백이 정상 동작해 2D 렌더러로 경기가 이어졌다.** 검은 화면이 아니라
호환 렌더로 내려앉는 것을 실제 사고로 확인한 셈이다(PATTERNS 8절 우아한 저하).

| 하단 | (+0.36, -0.30, -0.18) | y -0.12m |

두 군집**으로 정확히 갈렸다(1440x900). 선택은 렌더 전용 시드다.

### 화면 좌표를 쓰는 연출의 통로

캔버스 밖 DOM이 캔버스 위 같은 자리에 서려면 투영 좌표가 필요하다.
렌더러가 `setFxObserver(fn)`로 좌표를 넘기고 **그리는 것은 DOM(`FuiLayer`)이 한다.**
D5의 명중 마커와 데미지 표시가 같은 통로를 쓴다.

투영은 **월드 좌표 한 경로로 통일한다**(`projectToScreen`). 상대 빌보드 위 명중 지점처럼
카메라 로컬로 풀 수 없는 지점이 D5에 필요하므로 두 경로를 두지 않는다.

### 검끝 앵커를 심을 때의 함정 (D5-pre)

**`blade.worldToLocal(tip)`을 붙인 뒤에 부르면 안 된다.** `worldToLocal`은 그 시점의
`matrixWorld`를 쓰는데, 모델을 카메라 밑에 붙인 뒤에는 그것이 전혀 다른 공간이다.
실측으로 앵커 로컬 좌표가 `(-0.104, -2.652, 1.293)`이 나왔다(올바른 값은 `(0, 0, -0.822)`).

```js
// measure() 안에서 아직 독립 상태일 때 역행렬을 떠 둔다
const toBladeLocal = new THREE.Matrix4().copy(blade.matrixWorld).invert();
// 붙인 뒤에는 이 행렬만 쓴다
tipAnchor.position.copy(tip).applyMatrix4(toBladeLocal);
```

**이 모델은 로더가 -90도 X 회전을 얹는다.** glTF JSON의 노드에는 회전이 없지만
로드 후 칼날 장축이 -y로 온다(실측 `tipModel (0, -0.822, 0)`). 그래서 `measure()`는
축을 하드코딩하지 않고 Box3 장축으로 판별한다. 에셋을 갈아끼워도 같은 규칙이 돈다.

**1:1 검증.** 수정 뒤 앵커 로컬 `(-0.0001, 0, -0.8221)`, 월드가 해석값과 소수 3자리까지 일치한다.

| 자세 | 월드 좌표(실측 = 해석) | 화면 |
|---|---|---|
| 휴식 | (0.461, 1.404, -1.197) | **67.2% / 61.7%** (6절 설계 67.9 / 65.0) |
| 가드 | (-0.126, 1.919, -0.880) | **43.6% / 24.1%** (10-1절 설계값과 동일) |

**이 앵커는 검 모델 도입(9405f0d) 이후 줄곧 틀려 있었다.** 궤적 리본이 그 지점에서 나왔으므로
지금까지의 궤적은 칼끝이 아닌 곳에서 출발하고 있었다. 검과 함께 움직여서 그럴듯해 보였을 뿐이다.

### 리포스트 링

패리 지점에 팔각 미니 링이 서서 `RIPOSTE_WINDOW_MS`(600ms) 동안 줄어든다.

JUDGE 800ms 안의 타임라인이다. HUD의 `JudgeText`와 동기하며 **HUD는 수정하지 않는다.**

  렌더러가 시계를 만지지 않는다(3절 규율 유지).

### FUI 히트 마커와 데미지 인디케이터 (D5)

| 연출 | 조건 | 내용 |
|---|---|---|
| 명중 마커 | HIT/RIPOSTE, owner ME | 명중 지점에 팔각 레티클. 팔각 외곽 + 과녁 링 2겹 + red 꺾쇠 4개 + 부위 라벨 + `+1`(리포스트 `+2`) |

**명중 지점.** 내가 맞았으면 상대 검끝이다. 내가 넣었으면 **그립에서 칼끝으로 뻗은 직선을
상대 평면(빌보드 z)까지 늘린 곳**이고, 높이는 내 검끝 높이를 0.35~1.8로 죈 값이다.
가로는 실루엣 반폭의 0.9배 안으로 죈다. 밖으로 나가면 마커가 몸이 아니라 허공에 선다.
부위는 그 높이로 근사한다.

**E4 이전에는 가로가 상대 중심에 고정이라 어디를 찔러도 명중이 정중앙에 박혔다.**
높이도 찌르기 프리셋이 고정이라 부위가 항상 "투구" 하나였다.

**이 투영식은 임시가 아니라 미래 코드다.** C3에서 폰 쿼터니언이 검 그룹 회전을 쥐면
그 방향이 그대로 이 식에 들어와 코드 교체 없이 진짜 조준이 된다.
임시인 것은 아래 키보드 변주 하나뿐이다.

### 키보드 조준 변주 (E4, C3에서 제거)

키보드는 프리셋 트윈이라 찌르기 호가 매번 완전히 같다. 변주가 없으면 위 투영식이 옳아도
착탄이 한 점에 박힌다. **찌르기 시작 순간 한 번** 뽑아 칼끝을 민다(매 프레임 뽑으면 칼끝이 떤다).
그립은 그대로라 검이 겨냥을 바꾼 것으로 읽히고, 리본이 칼끝을 따라가므로 궤적도 매번 달라진다.

| 축 | 범위(카메라 로컬, m) | 왜 중앙값이 0이 아닌가 |
|---|---|---|
| x | -0.05 ~ +0.21 | 찌르기 프리셋의 칼끝이 그립보다 왼쪽이라 그대로 투영하면 착탄이 늘 몸 왼쪽에 몰린다(실측 -0.26m, 몸 반폭 0.50m라 절반이 한쪽 끝에서 잘린다) |
| y | -0.22 ~ +0.10 | 투구 문턱(1.55m)을 실제로 넘나들게 하려면 아래로 치우쳐야 한다 |

6절 안전 부등식 확인: 최대 |y| 0.17 대 한계 1.256, 최대 |x| 0.23 대 한계 1.674(4:3). 여유가 크다.

실측 200회(d 45, 런지 섞음): 착탄 x **-0.418 ~ +0.438m**, 평균 -0.015m, 좌우 끝에 물린 것 **0건**.
부위 라벨 투구 131 / 몸통 69. 실브라우저에서도 마커 화면 x가 108~144px 폭으로 흩어지고
투구와 몸통이 둘 다 나온다. **헤드리스는 5fps라 fx 시점의 검 자세가 뭉개지므로
분포 비율은 헤드리스로 재지 않는다**(13절 원칙과 같다). 비율은 위 200회 해석값이 기준이다.

| 높이 | 부위 |
|---|---|
| y > 1.55 | 투구 |
| y > 0.95 | 몸통 |
| 그 아래 | 팔다리 |

DOM 투영이라 데미지 표시는 피격 지점이 화면 밖이어도 그린다(프레임 가장자리에 서므로).
명중 마커는 화면 안일 때만 그린다.

## 12. 시간 팽창 시각

기존 `timeScale` 위에 시각을 얹는다. 로직은 그대로다.

| 항목 | 평시 | 발동 시 |
|---|---|---|
| `timeScale` | 1.0 | 0.35 (`tokens.motion.timeDilation.scale`) |
| 잔상 damp | 0.70 | 0.92 |
| Vignette | 약하게 | 강화 |
| HueSaturation 채도 | 0 | -0.4 |

지속 상한과 쿨다운은 `tokens.motion.timeDilation`(1200ms / 8000ms) 그대로다.
해제 시 전부 300ms 트윈으로 평시 복귀한다.
`reducedMotion`이면 engine이 팽창 자체를 발동하지 않으므로 이 세트도 서지 않는다.

## 13. 성능 예산과 감축

`tokens.motion.budget`: targetFps 60, minFps 30, trailMaxSegments 240, particleMax 300, afterimageMax 6.

minFps 아래로 일정 시간 머물면 순서대로 깎는다.

1. 파티클 상한 하향
2. AfterimagePass damp 하향
3. Bloom 해상도 하향

2D 경로의 자동 감축 가드를 three 경로에도 이식한다.

### 성능 미터 (?fps=1)

**헤드리스 소프트웨어 렌더링(SwiftShader)의 fps로 통과 판정을 하지 않는다.** 무효한 수치다.
V4b에서 후처리 도입 후 60 → 10fps로 떨어졌으나 실기 노트북에서는 거의 60(한 판 후 59 복귀)이었다.
에이전트가 보고할 수 있는 것은 **대리 지표**다. 드로우콜 수, 텍스처 수와 업로드 총량,
`render()` 함수의 CPU 프레임타임. 절대값이 아니라 전후 비교가 유효하다.

**최종 fps 게이트는 사용자의 실기 확인이다.** 그 확인이 dev 빌드 없이 가능해야 게이트가 성립하므로
**`?fps=1`이 붙으면 프로덕션 번들에서도 미터가 뜬다**(dev 빌드는 파라미터 없이도 뜬다).
미터는 현재 fps, 최근 60초 평균, 최저를 함께 낸다.
**최저는 순간 프레임의 역수가 아니라 1초 버킷의 최소 프레임 수다.** 프레임 하나의 역수는
GC 한 번에도 튀어서 읽을 수 없고, 1초 단위가 눈에 보이는 끊김과 단위가 같다.
미터는 상시 노출 요소라 애니메이션하지 않고 갱신은 초당 두 번으로 프레임 경로 밖이다.

## 15. 미해결 결정

구현 전에 확정이 필요한 것들이다.

  Lathe 자체 제작 안은 폐기했다(실물 모델이 훨씬 낫다)

- Bloom threshold와 intensity 초기값. **V4b에서 확정.**
  threshold 0.42, smoothing 0.28, intensity 1.15, radius 0.62, resolutionScale 0.5, kernelSize MEDIUM

남은 것

## 16. XR 글라스 팔각형 프레임

1인칭 시점을 화면 자체로 읽히게 한다. 각진 뷰포트가 참조각이되 색은 우리 것이다.
**블랙 + 크롬 + red.light. 파란 네온을 쓰지 않는다.**

### 구현

`arena/src/components/hud/GlassFrame.jsx`. 풀스크린 fixed SVG 한 장, `pointer-events: none`,
zIndex는 HUD와 같은 층에 두고 DOM 순서로 HUD가 위에 온다.

**viewBox 고정 스케일을 쓰지 않는다.** `preserveAspectRatio`로 늘리면 코너 각도가 종횡비를 따라 찌그러진다.
SVG를 뷰포트 실픽셀로 두고 `ResizeObserver`가 리사이즈에서만 여덟 점을 다시 계산한다.
스크롤이나 프레임마다 계산하지 않는다.

```
컷 크기 c = clamp(48px, 6vw, 120px)
팔각형   (c,0) (w-c,0) (w,c) (w,h-c) (w-c,h) (c,h) (0,h-c) (0,c)
```

겹은 셋이다. **CSS filter와 blur를 쓰지 않는다(합성 비용).**

1. 바깥 딤: `fill-rule="evenodd"`로 사각형에서 팔각형을 뺀 네 코너 삼각형. `bg.deep` 0.7
2. 크롬 스트로크: 팔각형 윤곽 1.75px. `linearGradient(steel.hi → mid → shadow → mid)`, `non-scaling-stroke`
3. 코너 액센트: 각 컷 변 안쪽 11px에 나란한 선분과 양끝 꺾쇠. `red.light` 2px.
   법선은 변에 수직인 두 후보 중 중심을 향하는 쪽을 고른다. 종횡비가 달라도 안쪽이 뒤집히지 않는다.
   **장식은 코너에만 두고 변 중앙은 비운다.**

상시 노출 요소라 애니메이션은 최초 1회 등장 페이드 300ms뿐이다(MOTION 0절). reduced에서는 등장도 생략한다.
arena는 1024 미만을 `ViewportGuard`가 차단하므로 프레임 미적용 분기가 따로 필요 없다.

### HUD 인셋 규칙

**모든 HUD 요소가 `frameInset(w) = cutSize(w) + 12px` 하나만 본다.** 컷 크기 + 12px이면
코너 삼각형(`x + y < c`)에서 넉넉히 벗어난다.

| 요소 | 위치 |
|---|---|
| 점수(나 red / 상대 blue) | 상단 좌측 컷 변 아래 안쪽 |
| StatusChip 3개 | 상단 우측 컷 안쪽 |
| 간합 게이지 | 하단 변 중앙 |
| PhaseBanner | 하단 우측 컷 안쪽 |
| JudgeText | **중앙.** 유일한 예외다 |

**중앙 시야는 비운다. 정보는 가장자리에만 둔다.** JudgeText만 남기는 이유는
800ms만 떴다 지는 판정 피드백이라 상주 정보가 아니기 때문이다.
미터가 켜지면 하단 행 전체가 62px 위로 비켜선다(배너만 올리면 1024에서 게이지 오른쪽 끝이 미터에 깔린다).
